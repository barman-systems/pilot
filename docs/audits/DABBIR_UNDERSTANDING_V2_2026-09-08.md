- قائمة الخدمات قد تستهلك الرسالة قبل المخطط وتفقد اليوم والوقت.
- الفهم موزع بين نص المحادثة وحالة انتظار، بلا مصدر وثقة لكل حقل.

- اكتشاف رسالة أحدث يسبق التفكير ولا يرتبط بمعاملة mutation نفسها.

## البنية

`durable queue → scoped context → semantic reducer → versioned state → policy gate → deterministic RPC → database readback → outbound reservation → Meta status evidence`

- `api/_dabbir-semantic-engine.js`: كيانات بمصادر وثقة، تصحيح يبطل السابق، فصل اليوم والوقت، إشارات إلى قوائم معروضة، سؤال للناقص، نماذج مفاهيمية قابلة للتوسعة.
- `api/_dabbir-understanding-orchestrator.js`: منسق واحد للفهم والسياسة والأدوات والتحقق؛ لا recursion أو حوار حر بين وكلاء.
- العامل والاسترداد يمران بالمنسق نفسه. تفريغ Voice Notes يدخل الدفعات نفسها، وثقة التفريغ مستقلة عن الدلالة والتشغيل. جودة الصوت غير المقاسة تبقى null.
- عند الحاجة يقترح النموذج نية/خدمة/مفتاح معرفة؛ لا ينفذ استنتاجه. تأكيد العميل أو الكتالوج مطلوب. جواب المعرفة يعاد من معرفة المالك المعتمدة.
- الحدود: استدعاء تخطيط منطقي واحد، حتى 4 محاولات مزود خلال 18 ثانية، 8 خطوات منسق وحد 25 ثانية. الحالات الشائعة بلا نموذج. معرفات قياس التكلفة منفصلة عن سياق النموذج.

تطوير الموجود:

- `dabbir_ai_conversation_state`: حالة دلالية ونسخة وربط بالدفعة وعداد الرسائل، FK مركب وFORCE RLS وحد 32 KiB.

- `dabbir_business_knowledge`: المعرفة المعتمدة ومراجع الاقتراحات.

جديد: `dabbir_ai_knowledge_proposals` للاقتراح/الموافقة/الرفض/الإلغاء/التراجع، و`dabbir_ai_understanding_events` للمقاييس والتدقيق بلا محتوى خام.

RPCs: `dabbir_semantic_load_v2`, `dabbir_semantic_commit_v2`, `dabbir_semantic_execute_v2`, `dabbir_semantic_set_pending_v2`, `dabbir_semantic_assert_current_v2`, `dabbir_semantic_reserve_outbound_v2`, `dabbir_knowledge_propose_v2`, `dabbir_knowledge_review_v2`.

`GET/POST /api/understanding-knowledge` يتطلب جلسة مالك النشاط؛ POST يتطلب same-origin. الاقتراح لا ينشط عند إنشائه؛ الموافقة مستقلة. جميع العمليات مسجلة بإصدارات. لا وصول anon. عمليات التشغيل للخادم فقط.

## الذاكرة والسلامة

الذاكرة مراجع لخدمة/عامل من مواعيد مكتملة، ومركبة/موقع من غسيل مكتمل أو مدفوع، أو آخر خدمة من حجز متحقق. آخر معلومة تشغيلية تختلف عن تفضيل دائم. لا تُستنتج عادة من زيارة واحدة. TTL 180 يومًا مع تحقق النطاق والكتالوج ومصدر التحقق. لا تُنسخ لوحات المركبات أو الإحداثيات إلى الذاكرة الدلالية؛ يحفظ مرجع داخلي.

لا mutation عند النقص أو الغموض أو انخفاض الثقة أو تدخل بشري أو تغيّر النسخة أو وصول رسالة جديدة أو إلغاء سياسة. الرسائل والأفعال تتسلسل بقفل صف المحادثة. الفعل الملتزم قبل وصول رسالة لاحقة لا يمكن إلغاؤه بأثر رجعي؛ الرسالة اللاحقة تصحيح جديد.

القائمة تبدأ `presented=false` ولا تُفعّل للاختيار حتى معرّف إرسال Meta. اختيار قائمة غير معروضة أو منتهية يمنع التنفيذ. operation key ثابت لكل batch/action. النتيجة المجهولة لا تعاد عميانيًا؛ يسمح بإعادة رفض HTTP 429 المؤكد. قبول المزود للرسالة منفصل عن تحقق التسليم من status webhook.

## التقييم

إعادة القياس: `node scripts/dabbir-understanding-evaluate.mjs`؛ التفاصيل في `DABBIR_UNDERSTANDING_V2_EVALUATION.json`.

- **71 سيناريو مميز، 139 حالة** تشمل متغيرات ترقيم ومسافات ورموز؛ ليست كلها سيناريوهات مستقلة.
- **139/139** عقدًا دلاليًا نجح، إضافة إلى فحوص SQL والأمان والربط.
- محلل الوقت القديم في 8 حالات مشتركة: **3/8 → 8/8**. هذه مقارنة المحلل الحتمي الفعلي، وليست مقارنة LLM كامل أو إنتاج.
- أعداد فحوص النية والكيانات والمراجع والتصحيحات والناقص والأداة مفصلة في JSON. العينات مصطنعة واستُخدمت أثناء التطوير؛ لا تدعي تعميمًا إحصائيًا أو تقييمًا مستقلًا.
- معدل إتمام الحجز الحي، الهلوسة الإنتاجية وخط الأساس الكامل للمزود **غير مقاسة بعد**.
- SQL جديد فعلي يعمل في PostgreSQL محلي عبر PGlite. أدوات الحجز السابقة ممثلة بمحولات fixtures في هذا الاختبار؛ لذلك لا يعادل تشغيلها الحقيقي على الإنتاج.
