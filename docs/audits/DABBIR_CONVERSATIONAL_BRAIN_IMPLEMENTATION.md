المحادثة الحقيقية المرصودة تضمنت كذلك «غسيل عادي» ثم سؤال المدة ثم «هي». أصلح main قبل هذه الموجة جانب سؤال المدة؛ أبقينا اختباراته وأضافت هذه الموجة اختبارًا لتأكيد «هي» دون إعادة تصنيف الهدف.

## المسار الفعلي بعد التنفيذ

WhatsApp webhook → دفعة رسائل وعميل موثوقان → `_dabbir-whatsapp-ai-core` → `runUnderstandingTurn` → `dabbir_semantic_load_v2` → snapshot النشاط/العميل/الحالة/العمليات → Context Resolver → المقترح الدلالي المحدود → reducer وcognitive goal continuity → validation لقرار التطبيق → CAS commit → أداة قراءة أو تعديل مخوّلة من حالة DB → تحقق النتيجة → سياسة صدق الرد → حجز إرسال idempotent وإيصال تقديم.

`api/ai-business-operator.js` هو مسار المالك ومحوّل الحجز؛ مسار رسائل WhatsApp الفعلي يمر بالـorchestrator المشترك المذكور. لم يُستبدل مسار المالك أو أدوات الحجز القائمة.

## الحالة المركزية

المصدر الوحيد: `dabbir_ai_conversation_state.semantic_state`، مع `semantic_version` و`semantic_message_revision` و`semantic_batch_id`. لا جدول ذاكرة ثانٍ ولا قاعدة بيانات جديدة.

لا تدّعي هذه الموجة تنفيذ حالة طلبات متجر، أو تحليل احتمالي كامل للمشاعر، أو ذاكرة دائمة لكل الكلام. هذه عناصر خارج الإثبات الحالي.

## حل السياق والهدف والقرار

`_dabbir-context-resolver.js` يفصل تسمية المرجع عن قيمته. النموذج يقترح أسماء حقول وإشارة مقتبسة فقط؛ لا يختار business/customer/branch IDs. المرجع ذو تاريخ صريح يقيّد العملية بتاريخ محلي في timezone النشاط. المعلومة الصريحة الحالية لها الأولوية، ثم الحالة النشطة للمرجع الحالي، ثم السجل التشغيلي المناسب أو ذاكرة موثقة. التعارض بين مصدرين لا يُحسم بترتيب الصفوف. اختلاف العميل/الفرع/النشاط، الحالة التجريبية أو الملغاة، انتهاء الذاكرة، أو حذف الخدمة يمنع إعادة استخدامها.

التصنيف يبقى metadata داخل المخطط الحالي؛ `cognitiveReduce` يحافظ على هدف الحجز خلال الأجوبة والتصحيح والسؤال الجانبي. القرار النهائي يتحقق منه `assertBrainDecision` قبل الحفظ، وتظل صلاحيات SQL هي الحاسمة. لم نضف Model أو Provider أو Framework أو استدعاء LLM جديدًا. استُخدم schema الحالي المتوافق مع المزود وZod المثبت أصلًا؛ لم تُضف dependency.

## التنفيذ ومنع الادعاء

- `dabbir_semantic_check_availability_v1(batch, lock, version)` يستخرج الخدمة والعميل والفرع من الحالة المحفوظة، وينفذ أداة التوفر الحالية ويحفظ إيصال القراءة في المعاملة نفسها.
- لا يمكن لنتيجة فارغة البنية أو موعد لخدمة/موظف خارج السياق أن تتحول إلى موعد معروض أو ادعاء عدم التوفر.
- إنشاء/تعديل/إلغاء الحجز بقي عبر `dabbir_semantic_execute_v2` ودفتر idempotency الحالي، مع إعادة تحقق جديدة من المصدر التاريخي قبل التنفيذ.
- الرد التشغيلي يتولد بعد النتيجة الموثقة. أضيف backstop يمنع عبارات نجاح معروفة دون إيصال مطابق والوعود المستقبلية غير المسجلة. هذه حماية إضافية محدودة وليست برهانًا لغويًا عامًا لكل صياغة ممكنة.
- observability يسجل مصدر المرجع والحقول والقرار ونتيجة القراءة؛ لا يخزن chain-of-thought أو نص المرجع في المقاييس.

## الترحيل والتحقق الحي والرجوع

الترحيل المطبق: `20260909180619_dabbir_conversational_brain_context_v1.sql`. أضاف hydration تاريخي وحماية مصدر وRPC قراءة محمية. لم يحذف صفًا أو جدولًا، ولم يغير RLS أو صلاحية عميل. الأداة الجديدة محظورة على anon/authenticated ومتاحة للخادم فقط.

نجح `DABBIR_BRAIN_PRODUCTION_SMOKE.sql` على مشروع Mumbai الحقيقي: load/commit/replay، التوفر المركزي وحفظ نتيجته، قراءة التاريخ وإعادة التحقق منه، الحجز والتعديل والإلغاء، منع GPS المستنتج والمركبة المفقودة والحالة التي تجاوزتها رسالة أحدث، وعدم تكرار الحجز. جميع صفوف الاختبار داخل rollback. إيصال WhatsApp في هذا الاختبار اصطناعي وموسوم بذلك صراحة.

حماية Production رفضت إدخال موعد تاريخي في الماضي في محاولة إعداد fixture؛ بقيت الحماية كما هي، واستُخدمت عملية مكتملة اصطناعية في الدقيقة الحالية. حساب «أمس» عبر timezones مثبت بالـBenchmark، وليس بتحوير ساعة الإنتاج أو تعطيل trigger.

الرجوع: إعادة التطبيق إلى SHA السابق يعيد المسار السابق مع بقاء الترحيل الإضافي متوافقًا. ضبط cognitive rollout الموجود إلى shadow/off يعيد المسار القديم للنشاط وفق صلاحيات الخادم القائمة. لا يلزم حذف الحالة أو الذاكرة أو إسقاط الدوال الجديدة. لو احتاجت قاعدة البيانات رجوعًا، تعاد دالتا load/execute من نسخة ما قبل الترحيل بعد مراجعة أي تغييرات لاحقة؛ لا rollback أعمى.
